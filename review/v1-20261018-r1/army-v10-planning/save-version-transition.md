# 꼬마 군단 원정대 1.0: 저장·버전 전환 계약

작성: 2026-10-18 UTC  
상태: 승인된 로컬 1.0 설계의 일부. 제품 코드, 실제 저장, 배포, 외부 서비스는 변경하지 않았다. 아래 새 스키마·식별자·거래 구조는 구현 명세 제안이며 구현 완료를 뜻하지 않는다. 로그인·클라우드 백엔드·랭킹은 범위 밖이다.

## 1. 반드시 지킬 전환 정책

1. **진행 중인 0.9 원정은 원래 2장 규칙으로 끝낸다.** 지도·조우·전투·보상 RNG·상점·훈련·정산을 도중에 1.0으로 교체하지 않는다. 2장 보스를 잡았을 때 3장으로 이어 붙이지 않는다.
2. **종료 뒤 새로 시작하는 원정부터 1.0의 5장 규칙을 사용한다.** 승리·패배·퇴각 모두 같은 경계다. 사용자가 새 출정을 선택하기 전에는 종료 화면/원래 정산 결과를 보존한다.
3. 프로필의 보유 증표, 기존 유물·갈래·훈련·전술 해금, 기존 기록과 정산 원장은 보존한다. 새 버전 설치 보상·자동 해금·가상 승리·가상 완주는 만들지 않는다.
4. 원정의 골드·병사·훈련·유물·컨디션·획득 예정 증표는 다음 원정으로 옮기지 않는다. 원정 종료 시 해당 구규칙으로 정산한 증표와 영구 해금만 프로필로 넘어간다.
5. 0.9에서 훈련 II를 마친 병사를 가져왔다고 새 2차/3차나 기술을 소급 지급하지 않는다. 구버전의 진화 갈래를 2차로 재명명하지 않는다.
6. 가져오기는 검증된 저장의 **교체**다. 별개 파일들의 증표·해금을 합집합/합산하거나 낮은 값을 높은 값으로 자동 보정하지 않는다. 교체 전 현재 저장의 안전 백업과 사용자 확인 흐름을 유지한다.

5장, 3장 수집→4장 궁극→5장 활용, 2차 기본 기술 2개 및 3차 동일 2개+궁극 1개는 사용자 확정 구조다. 장당 최소7전투는 보스 포함 해석이며 기본35전투·34보상 기회·새 경제 수치·각성 한도·발동 방식은 비교 설계안이다. 이 문서가 미확정 게임 수치를 확정하지 않는다.

## 2. 현재 코드에서 확인한 사실

| 영역 | 실제 0.9 계약 | 1.0에서 필요한 분리 |
|---|---|---|
| 저장 봉투 | schemaVersion=3, rulesVersion=v09-campaign-1 | 봉투 형식과 원정 규칙을 별개로 선택 |
| 원정 버전 | campaignRulesVersion=v09-campaign-1, mapVersion=v09-operations-1, combatRulesVersion=v09-combat-1 | 새 조합을 명시 등록, 임의 혼합 불허 |
| 지도 | 2장, 후보 32개. 시드로 재생성한 전체 노드/조우와 정확 비교 | 구 생성기는 그대로 두고 새 5장 생성기 추가 |
| 진행 | 연결된 visited, completed는 그 접두사, xp===completed.length | 구0.9는 그대로 보존. 새1.0은 실제 경로와 별도 XP 원장 검증; 빈 합류 완료 없음 |
| 프로필 | version=2, bestChapter 0~2, 증표·4종 해금 목록·settledRunIds | 5장 기록과 구 2장 완주 의미를 구분 |
| RNG | seed/rngState, rewardRngState/rewardRollCounter, battleSeed | 새 기능별 결정적 입력/버전과 소비 경계 필요 |
| 저장 트랜잭션 | 복제→변경→검증→저장/읽기 확인, 실패 시 메모리 복원; revision/nonce/다른 창 충돌 검사 | 새 성장·목표·각성·정산도 동일 경계에 포함 |
| 재개 | battle 저장을 load/import 시 prepare로 되돌림 | 중간 전투 재개가 아니라 전투 전 체크포인트 재시도 |
| 이전 형식 | schema 1/2를 검증 후 봉투로 감싸며 구규칙 유지 가능 | 오래된 규칙도 1.0 규칙으로 위조하지 않음 |

특히 campaign.js 앞부분은 보존된 0.8 코드다. 현재 0.9 검증은 뒤의 별도 블록을 기준으로 읽어야 한다. 단순히 앞쪽 장 범위 또는 SCHEMA_VERSION 하나를 바꿔서는 전환이 성립하지 않는다.

## 3. 버전의 의미와 권고 저장 구조

### 버전 축

- schemaVersion: 필드 배치·타입·직렬화 형식. 숫자가 증가해도 게임 규칙을 바꾸는 허가가 아니다.
- campaignRulesVersion: 5장 진행, 성장 자격, 경제·보상·정산·목표 경계 계약.
- mapVersion: 토폴로지·노드 ID·템플릿 선택·조우 생성. 표시 축약과 논리 삭제를 구분한다.
- combatRulesVersion: 실제 행동, 우선순위, 대상 동률 해소, RNG·틱·입력 해석·계수.
- contentVersion: 신규 직업·기술·유물 정의의 불변 묶음. 구규칙 생성기가 최신 전역 정의를 읽어 내용이 바뀌지 않게 한다.
- profileVersion: 영구 해금·기록 표현. 원정의 전직 단계와 별개다.

제안 이름은 schema 4, v10-campaign-1, v10-operations-1, v10-combat-1, v10-content-1이다. 아직 등록/구현되지 않은 이름이며, 정의가 검증되기 전 저장을 이 이름으로 찍지 않는다. 등록된 완전한 조합만 허용한다. 예를 들어 0.9 지도+1.0 전투는 같은 시드라도 허용하지 않는다.

### 호환 래퍼 우선안

새 봉투는 `schemaVersion`, `envelopeRevision`, `payloadKind`, `payload`를 갖는 구조로 설계한다. payloadKind는 legacy-save 또는 v10-save 중 하나다. 구 payload에는 기존 검증을 통과한 전체 저장(구 프로필 포함)을 그대로 둔다. 새 payload에는 1.0 규칙·프로필·원정을 둔다. **이 구조는 제안이지 현재 export 형식이 아니다.**

- legacy-save를 읽을 때 내부 저장은 기존 migrateSave/validator/runner로 처리한다. 봉투만 새 형식이고 내부의 구 스키마·규칙은 유지된다.
- 기존 프로필 검증이 허용하지 않는 5장 기록이나 신규 해금 ID를 구 프로필에 밀어 넣지 않는다. 구 runner는 구 프로필을 갖고 종료까지 실행한다.
- 구 원정 종료 이후 새 출정 거래 하나에서 구 프로필을 새 표현으로 변환하고 새로운 1.0 원정을 만든다. 그 전 구 payload는 안전 백업으로 보존한다.
- 새로운 저장 위치는 예를 들어 tiny-army-v10-save로 분리한다. 유효한 새 저장이 있으면 오래된 키로 자동 되돌아가지 않는다. 새 저장이 손상되었다면 덮어쓰기 차단·복구 안내이며, 구 저장 재시작으로 성과가 되감겼음을 숨기지 않는다.
- 이전 키는 삭제하지 않는다. 새 저장의 생성/검증/재읽기 성공 전에는 전환 완료로 표시하지 않는다. 서로 다른 키를 원자적으로 바꾸었다고 가정하지 않고, 새 봉투 하나를 활성 원본으로 삼는다.
- 구 앱에서 새 형식을 읽는 역방향 변환은 제공하지 않는다. 보존된 구 백업은 전환 당시 기록일 뿐 새 1.0 성과를 포함하지 않는다. 구 앱을 다시 열면 분기 진행이 생길 수 있으므로 두 파일을 합치지 않는다.

## 4. 프로필 보존과 종료 한 번만 정산

### 변환 함수의 허용 범위

구 프로필 검증 성공 → 토큰 정수 그대로 복사 → 기존 해금 ID 그대로 보존 → 기록 출처를 구규칙으로 표시 → 정산된 runId 전체 보존 → 새 프로필 검증의 순서다. 현재 limits(증표 1e9, 원장 10000개 등)를 초과하면 조용히 자르지 않고 전환을 중단한다. 확장/압축 정책은 별도 명세와 테스트가 필요하다.

기록은 기존 runs/wins/battles를 누적 이력으로 보존하되 구 완주를 5장 완주로 표시하지 않는다. 기존 bestChapter=2는 **구 2장 체계의 최고 2장**으로 보관하고, 새 규칙별 기록은 새 원정부터 누적한다. 이미 구체계가 섞인 누적 기록을 억지로 각 버전별로 분해하지 않고 legacyAggregate로 남긴다. 초기 v10 기록 0은 새 카운터이며 과거를 삭제한 값이 아니다.

신규 프로필은 기존 ID 의미를 잃지 않는 해금 레지스트리를 가진다. 신규 열쇠/연구/목표 경로 자격은 1.0 규칙에 명시된 기본 자격 또는 실제 해금 거래로만 생긴다. 과거 갈래 해금이 신규 궁극 해금이었다고 추정하지 않는다. 새 필수 자격이 추가되면 궁극 자격과 목표 열쇠 경로가 함께 열리는지 검사한다.

### 정산 원칙

- 진행 중 earnedTokens를 profile.tokens에 합산하지 않는다.
- 구 원정은 구 token 식과 완주 보너스(현행 +8)를 그대로 사용한다. 장을 늘렸다는 이유로 과거 보너스/증표를 다시 계산하지 않는다.
- 정산 거래는 runId, outcome, earnedTokens, bonus, unlocks, 기록 변화와 settledRunIds 삽입을 한 저장에 담는다.
- 종료된 구 저장을 읽거나 새 출정을 만드는 것은 재정산 사유가 아니다. 같은 runId가 원장에 있으면 지급하지 않는다.
- 새 정산은 새 캠페인 규칙표를 사용한다. 5장 경제안의 제안 값을 구 validator에 일반화하지 않는다.
- 원정 ID는 충돌하지 않는 거래 식별자다. Date.now/Math.random 기반 현재 ID를 결정적 게임 시드로 사용하지 않는다. 동일 시드의 별개 원정은 서로 다른 runId와 별개 정산이다.

## 5. 병사·기술·열쇠의 안정된 정체성

### 병사와 전직

1. unitId는 모집부터 종료까지 불변이다. 1차→2차→3차, 출전↔예비, 훈련 후에도 새 병사로 교체하지 않는다.
2. 기본 계열(family), 기존 1차 역할(parentType), 전직 단계(progressionStage), 선택한 specializationId, trainingTrack/training을 구분한다. 표시 이름은 식별자가 아니다.
3. 2차에서는 정의 레지스트리의 정확한 basicSkillIds[2]를 사용한다. 3차는 동일한 두 ID를 유지하고 ultimateSkillId 하나만 추가한다. 평타는 이 두 개에 포함하지 않는다.
4. 병사 기술과 기존 run.skills의 지휘 기술 2칸을 섞지 않는다. 입력/효과 로그에도 commander-skill과 unit-skill 출처를 구분한다.
5. 기존 역할별 8개 2차 및 16개 훈련 변형을 표현하되 훈련마다 임의 새 병사/기술 슬롯을 만들지 않는다. 조건을 마지막으로 채우는 성장 거래에서 단계와 두 기술을 함께 개방하는 기본안을 적용할 경우, 거래 전후가 모두 합법 상태여야 한다.
6. 저장에는 직업/기술 정의 ID와 버전을 저장하고 실행 함수·클라이언트가 주장한 임의 계수는 받지 않는다. 저장된 기술 목록을 중복 저장한다면 레지스트리에서 도출한 목록과 정확히 같아야 한다. 모르는 ID를 가장 비슷한 기술로 교체하지 않는다.

### 열쇠의 정체성과 자격

| 계열 | 제안 영구 정의 ID | 3차 연결 |
|---|---|---|
| spear | iron_oath | 불굴의 선봉의 수성/돌파 분기 |
| archer | eagle_signet | 천공의 명수의 일점/탄막 분기 |
| mage | arcane_seed | 비전의 현자의 홍련/한파 분기 |
| support | covenant_lamp | 생명의 수호자의 구명/방호 분기 |

위 ID는 class-skill-progression.md의 제안과 일치시키며 실제 기존 레지스트리에 존재한다고 주장하지 않는다. 같은 유물의 I/II/III는 같은 relicId와 evolution 값이다. 희귀도·진화·궁극 계열·목표 보상 ID는 서로 다른 개념이다. 보유 목록에는 같은 정의 유물 중복을 금지하는 현재 정책을 계승한다.

각성 receipt에는 unitId, 부모 2차 ID, 기존 기본 기술 두 ID, ultimateId/ultimateSkillId, requiredRelicId, 확인한 진화 단계, 기회 ID, rulesVersion, 거래 revision을 기록한다. 열쇠 I 인정/비소비·원정 1명·0G 기본안을 채택하면 그 값도 규칙에 고정한다. 보유한 열쇠 개수만으로 각성 사용 횟수를 도출하지 않는다. 4장 진입 지도 패널의 선택과 취소/거절 상태를 저장한다. 별도 M1 합류 대안은 없으며 패널 재열기로 새 각성 기회를 만들지 않는다. 3장 보상에서 열쇠를 얻는 거래와 4장 각성 거래는 별개다.

## 6. 시드·결정적 입력·재현 범위

같은 숫자 시드만으로 모든 플레이가 동일하다고 약속하지 않는다. 재현 묶음은 규칙/콘텐츠 버전 + 시드 + 출정 자격 스냅샷 + 시작 전술/유물 + 경로/보상/상점/성장 선택 + 전투 시작 편성/상태 + 입력 로그다.

- 지도·조우·보상·상점·전투의 RNG를 분리한다. seed에서 버전/용도별 고정 namespace로 파생하고 상태 및 소비 카운터를 저장한다. 현행 구규칙의 파생 문자열과 RNG 소비는 바꾸지 않는다.
- 지도 열기, 경로 비교, 기술 설명, 보상 카테고리 미리보기, 각성 자격 열람, 창 닫기/다시 열기에는 RNG 소비가 없다.
- 보상 후보 생성과 유료 리롤만 정의된 보상 스트림을 소비한다. 생성 결과·generation·nonce·리롤 횟수를 먼저 같은 거래로 저장하고, 재개 때 다시 뽑지 않는다.
- 3장 목표 확정은 targetId, 해당 unitId/family 기준, 확정 revision, 목표 재고/보상 경로 정의를 기록한다. 교대/재접속으로 목표를 재선택하지 않는다. 목표 변경은 별도 규칙 승인 전 허용하지 않는다.
- 전투는 고정 틱, 안정된 병사/적 ID, 대상 동률 해소 순서, 이벤트 정렬, RNG를 명세한다. 프레임 속도·애니메이션 완료 시간·Date.now를 전투 결과 입력으로 쓰지 않는다.
- 입력은 battleId, tick, sequence, actorUnitId(병사 궁극인 경우), skillId, targetId 또는 명시된 대상 없음, 입력 종류를 기록한다. 같은 tick의 순서·허용 범위·중복/역순 입력 처리도 버전화한다. 자동 행동은 동일 상태에서 도출하되 원인 actionId로 효과를 추적한다.
- 궁극 준비/확정/사용/변환 소모와 부모 기본 기술 ID를 구분한다. 무효 대상에서 기다리는 것과 유효 행동 확정 후 빗나가는 것을 구분하며, 후자만 부분 롤백해 사용권을 돌려주지 않는다.
- 로컬 저장 검증은 암호학적 치트 방지나 전투 진실성 증명이 아니다. 현재 결과 검증도 전체 전투 재실행 증명이 아니다. 재현 테스트와 구조 검증의 범위를 명확히 표시한다.

## 7. 보상·거래·재접속 경계

모든 변경은 `현재 원본/버전 확인 → 복제 → 자격/nonce/revision 재검사 → 전체 효과 반영 → 전체 저장 검증 → 한 봉투 쓰기/읽기 확인 → 메모리 확정` 순서로 설계한다. 저장 실패 시 성공 애니메이션/구매 완료를 먼저 확정하지 않는다. 쓰기 성공 여부가 불명확하면 원본을 재확인하고, 새 nonce로 무조건 재시도하지 않는다.

|---|---|---|

### 전투 중 종료 정책

초기 1.0 권고는 현재처럼 **전투 시작 전 체크포인트 재시도**다. 전투 중 저장을 읽으면 prepare로 돌아간다는 사실을 표시하며 같은 battleSeed/노드를 보존한다. 미확정 전투의 HP·마나·궁극 사용을 부분적으로 보존하거나 보상만 지급하지 않는다. 결과가 이미 확정된 전투는 재시작할 수 없다.

이는 중간 틱 복원이나 재접속 악용 방지 보장이 아니다. 재시도에서는 전투 전체가 다시 시작되므로 궁극을 포함한 모든 전투 내 상태가 시작 상태로 돌아간다. 준비에서 편성을 바꾸거나 새 입력을 하면 같은 결과를 보장하지 않는다. **궁극 사용 뒤 같은 전투 중간으로 돌아가 사용권만 복원하는 방식은 금지**다. 미래에 중간 복원을 도입하려면 모든 개체·투사체·장판·RNG·행동 큐·마나·쿨다운·궁극·입력 인덱스를 같은 틱에 저장하는 별도 combat 버전이 필요하다.

## 8. 가져오기 검증: 복구를 가장해 내용을 발명하지 않는다

1. 현재 2MB 제한 등 크기·깊이·배열 길이·문자열·유한수·안전 키를 먼저 검사한다. 5장 파일에 제한 변경이 필요하면 실측·상한 설계를 거친다.
2. 지원하는 정확한 봉투/규칙 조합을 판별한다. 미래 버전·미등록 조합은 원본 보존 후 거절한다.
3. legacy payload는 해당 구 validator로 검증한다. 구 장 범위, 32후보, 구 토큰/정산식을 1.0 한도로 느슨하게 바꾸지 않는다.
4. v10은 저장된 generatorVersion/rulesVersion/graphHash와 전체 생성 지도·조우를 대조한다. 실제 간선에 따른 완료 경로, 중복 완료, phase, 보스/전환, 보상 원장을 검증한다. 기본안은 장당 후보 최대21, 원정 최대105후보·35전투·선택 서비스0~10회다. 완료 노드 개수와 XP를 동일시하지 않는다. XP 증분3/1/1/1/1/2/1·장10/총50은 미확정 제안이며 버전별 XP 원장 합계로 검증한다. seed만 저장해 최신 생성기로 교체하지 않는다.
5. 병사 ID/슬롯/정원·계열/단계·훈련·기술 계승·열쇠·각성 receipt·목표 고정·거래 중복을 교차 검증한다. 플레이어가 저장에 넣은 displayName으로 정의를 찾아 추측하지 않는다.
6. 결과/완료/증표/예비 회복/보상/정산 원장을 교차 검증한다. 누락 receipt·RNG 상태·부모 기술·열쇠를 만들어 메우지 않는다. 기대 보상은 실제 확정한 규칙표에서 계산한다.
7. 모든 검증이 끝난 뒤 현재 원본 백업을 쓰고 읽기 확인한다. 백업 실패 시 교체하지 않는다. 교체할 새 봉투를 검증·저장·읽기 확인한 뒤 메모리를 바꾼다.
8. 실패 메시지는 지원 안 되는 버전, 손상, 저장소 실패, 다른 창 충돌을 구분한다. 원본을 내보낼 수 있게 하고, 빈 프로필로 자동 덮어쓰지 않는다.

허용되는 구조 변환은 알려진 필드의 무손실 이동/버전 포장과 명시된 기본값뿐이다. 예를 들어 v10 신규 기록 카운터를 0으로 만들 수는 있지만, 누락된 구 증표를 0으로 고치거나 훈련 II에 기술 두 개를 소급 발명할 수는 없다. 가져온 과거 저장으로의 복원은 되감기를 동반할 수 있다. 오프라인 파일을 여러 번 복원하는 행위를 전역에서 막을 수 있다고 주장하지 않는다.

## 9. 승인 후 구현 순서와 중단 기준

1. **구규칙 고정:** 대표 시드·각 phase·정산·해금의 실제 0.9 fixtures를 보관하고 기존 map/content/combat/RNG 동작 회귀를 잡는다. 0.5/0.8 호환도 현재 지원 범위 내 유지한다.
2. **레지스트리와 봉투:** 버전 조합 dispatcher, 불변 정의 묶음, 새 저장 위치, legacy wrapper, 원본 백업/복구를 구현한다. 구 원정은 아직 새 성장 기능을 보지 않는다.
3. **프로필 전환:** 종료 상태에서만 변환, 증표/해금/원장 보존, 구 기록 표시, 새 출정 원자성을 구현한다.
4. **5장 지도와 진행:** 새 생성기/검증기, 장 전환·완주, 전투 완료/별도XP 원장·무료 직행·장 진입 각성 경계를 구현한다. 기존 생성기를 수정해 범용화하지 않는다.
5. **새 성장 모델:** unitId·계열·부모·단계, 2기술, 추가 궁극, 열쇠/목표/각성 receipt를 구현한다. 선택된 실제 발동 규칙이 없으면 combat 버전 공개를 막는다.
6. **거래와 결정성:** 보상·상점·성장·연구·제련·목표·각성·정산, 독립 RNG, 입력/행동 로그와 저장 실패 복구를 검증한다.
7. **가져오기/내보내기/UX:** 지원 버전 표시, 구 2장 이어하기·새 5장 시작 구별, 전투 재시도 안내, 백업/충돌 안내를 연결한다.
8. **호환·경계 테스트 후 판단:** 아래 행렬 통과와 밸런스/콘텐츠 검증을 별개로 확인한다. 구현/테스트/배포 승인은 이 문서 작성으로 대체되지 않는다. 실패 시 구 저장을 변경하지 않고 신규 전환을 중지한다.

## 유물 획득 범위의 공통 계약

72후보·첫25검증/조건부11/후속36을 보존한다. 일반 후보는 현재 출전/지휘, 지정 목표 검색은 예비 포함 보유 전체를 검사한다. 목표는 열쇠 또는 비궁극 핵심 유물이며 정예·상점0회 경로에도3장 보스(전체21) 보상 안의 한 슬롯을 확보한다. 카테고리 → 희귀도 → 적격 ID → 사전 고정 fallback 순서와 동일 선택 예산을 지킨다. 중복·편성 변경·포화·재접속으로 재추첨하거나 추가 보상을 주지 않는다. 34회는 전체 선택 기회이며 유물 수가 아니다. 가중치·가격·fallback 가치·XP 배분은 미확정이다. 세부 효과/대가/현재·미래·각성 자격 preview는 relic-catalog.md §3·§8을 따른다. 신규8종·35전투 실전 검증 완료를 주장하지 않는다.
